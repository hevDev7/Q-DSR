# ERC-7857 conformance

What this implementation does, what it does not, and where it deliberately
departs from the draft. Written so a reviewer who knows the standard does not
have to reverse-engineer the answer from the source.

Reference: [0G — ERC-7857](https://docs.0g.ai/developer-hub/building-on-0g/agentic-id/erc7857)

---

## The interface

The draft declares:

```solidity
interface IERC7857 is IERC721 {
    function transfer(address from, address to, uint256 tokenId,
                      bytes calldata sealedKey, bytes calldata proof) external;
    function clone(address to, uint256 tokenId,
                   bytes calldata sealedKey, bytes calldata proof) external returns (uint256);
    function authorizeUsage(uint256 tokenId, address executor,
                            bytes calldata permissions) external;
}
```

`AgenticID` implements all three, declared through our own `IERC7857` which also
extends `IERC721`, and answers ERC-165 for it:

```
ERC7857_INTERFACE_ID = type(IERC7857).interfaceId = 0x76b2298c
```

Solidity excludes inherited functions from `type(I).interfaceId`, so that value
covers exactly the three calls ERC-7857 adds. A caller asking "is this an Agentic
ID" gets a yes; a block explorer that only knows the registered standards will
still print ERC-721, which is true and merely less specific.

| | |
|---|---|
| `transfer(from, to, tokenId, sealedKey, proof)` | ✅ implemented |
| `clone(to, tokenId, sealedKey, proof)` | ✅ implemented |
| `authorizeUsage(tokenId, executor, permissions)` | ✅ implemented |
| `event MetadataUpdated` | ✅ emitted on transfer and clone |
| `event UsageAuthorized` | ✅ emitted |
| `event OracleUpdated` | ❌ not emitted — the oracle is `immutable` here, so it never changes |
| ERC-165 detection | ✅ `0x76b2298c` |

## Minting

The draft specifies no mint function. The reference implementation shows an
owner-restricted one:

```solidity
function mint(address to, string calldata encryptedURI, bytes32 metadataHash)
    external onlyOwner returns (uint256)
```

Ours replaces the owner check with a certification check and carries richer
metadata:

```solidity
function mint(address to, bytes32 agentId, AgentMetadata calldata metadata, bytes32 metadataHash)
    external returns (uint256)
```

Two departures, both deliberate:

**It is permissionless.** Anyone may mint for a certified agent. An allowlist on
top of the statistical gate would only mean a second gatekeeper, and the whole
argument of this protocol is that the statistical one should be the binding one.

**It is gated on `registry.isCertified(agentId)`.** An agent whose evidence has
not survived PBO and DSR testing cannot acquire an identity at all. That gate is
the product.

## Where this implementation departs from the draft

### Metadata is public, not encrypted

The standard's premise is that an agent's intelligence is encrypted, and that the
oracle re-encrypts it during transfer so plaintext is never exposed.

This protocol certifies *backtests*, and its entire claim is that a stranger can
re-run the evidence and reproduce the verdict. Encrypting that evidence would
make the claim uncheckable. So the returns, the trials matrix and the bootstrap
artifacts are published to 0G Storage in the clear, on purpose, and `evidenceURI`
is named for what it holds rather than borrowing the reference implementation's
`encryptedURI`.

**We do not perform re-encryption.** A sealed key is accepted, stored and
replaced on every transfer and clone, and its hash is announced through
`MetadataUpdated` — but this contract does not encrypt, decrypt or re-encrypt
anything. It records what a caller supplies. An implementation that needs the
standard's confidentiality guarantees needs an oracle that actually performs the
re-encryption; this one does not pretend to.

Storing the key rather than discarding it matters: validating a sealed key and
then throwing it away would be worse than not accepting one, because it looks
like the key travelled with the token when it did not.

### The oracle answers a different question

The draft's `verifyProof` is meant to attest that a re-encryption was performed
correctly — the proof carries a metadata hash and the receiver's public key.

Ours implements the same hook with different semantics: `proof` is an
abi-encoded `agentId`, and `verifyProof` answers whether that agent holds a
passing verdict.

That is a reuse of the extension point, not an implementation of its intended
meaning, and it is worth being explicit about. The reason is that the hook is the
only place the standard offers for a contract to consult external judgement
before an operation proceeds, and certification is the judgement this protocol
exists to enforce. A production system wanting both would need two oracles.

### tokenURI

The draft does not define metadata behaviour. `tokenURI` here returns a base64
`data:application/json` document built in the contract, carrying the verdict, the
Deflated Sharpe Ratio, the Probability of Backtest Overfitting, the trial count
and the observation count as attributes.

The numbers are read live from the registry rather than copied at mint time, so a
token whose agent later fails re-verification stops claiming to be certified.

Artwork is an http(s) URL, in practice served from 0G Storage. With none supplied
the contract draws an SVG from the agent's own numbers, so a token always renders
without any hosting.

## Summary

| Aspect | Status |
|---|---|
| Interface functions | Implemented |
| ERC-165 identification | Implemented |
| Standard events | `MetadataUpdated`, `UsageAuthorized` implemented; `OracleUpdated` not applicable |
| Sealed key lifecycle | Recorded and replaced, **not** re-encrypted |
| Encrypted metadata | **Not implemented** — evidence is public by design |
| Oracle semantics | Hook reused for certification, **not** re-encryption proof |
| Minting | Extension: permissionless, gated on certification |
| tokenURI | Extension: on-chain JSON carrying the certification |

The short version: the surface conforms, the confidentiality model does not, and
the difference is a design choice rather than an omission — a protocol whose
point is public verifiability cannot also hide its evidence.
